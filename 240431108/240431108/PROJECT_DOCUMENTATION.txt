1. PROJECT PROFILE

1.1 Definition

Project Name:
Luxe Hotel & Dine

Project Type:
Static hospitality and food-ordering website with PHP/MySQL backend.

Project Purpose:
The project presents a hotel and dining website where users can view services, browse rooms, place food orders, register, log in, submit reviews, and proceed through a payment form. It is intended to digitize a portion of hospitality operations that would otherwise be manual.

Problem Being Solved:
The conventional workflow for hotel and food services often relies on manual communication, physical records, and informal processing. This project aims to replace some of those manual steps with digital forms and database-backed records.

Target Users:
- hotel visitors
- customers looking for room information
- users ordering food
- users creating an account
- reviewers submitting feedback

Main Functionality:
- homepage and service overview
- room browsing and details
- food ordering form
- user registration
- login system
- payment submission form
- guest review form
- MySQL database integration

Overall Workflow:
A user visits the website, navigates through pages, registers or logs in, places food orders, continues to payment, and submits reviews. Data is sent from the browser to PHP scripts, which validate and store it in MySQL tables.

Technology Architecture:
- Frontend: HTML, CSS, JavaScript
- Backend: PHP
- Database: MySQL
- Server environment: XAMPP-compatible Apache + MySQL
- Communication: browser fetch() to PHP scripts

Frontend:
The frontend consists of static HTML pages and CSS/JavaScript for design, animations, validation, and navigation. Pages include index.html, about.html, room.html, room-1.html to room-8.html, order.html, payment.html, review.html, login.html, sign-up.html, galary.html, team.html, popular.html, our_food.html, burger.html.

Backend:
The backend is implemented in PHP files under php/:
- db_connect.php
- register.php
- login.php
- order.php
- payment.php
- review.php

These scripts validate data, connect to MySQL, insert records, and return JSON responses.

Database:
Database schema and setup scripts are under php/database/ and php/luxe_hotel.sql. Tables created include:
- users
- orders
- payments
- reviews
- bookings

API Communication:
The frontend uses fetch() to send form data to PHP endpoints. There is no formal REST framework in the project.

Authentication:
The login flow uses PHP session_start() and stores values in $_SESSION. There is no role-based authorization system in the code.

Major Modules:
- home/landing page
- room showcase
- food ordering
- user registration
- login system
- payment submission
- review submission
- database setup scripts

Important Features:
- stylish responsive layout
- animations and user interaction
- validation for login and registration
- password hashing for users
- session-based login state
- order calculation logic
- card-last4 storage for security

2. SYSTEM ANALYSIS AND SPECIFICATION

2.1 Existing System

The project targets a typical hospitality workflow that originally depends on manual processes such as direct contact, paper records, and informal customer handling. This system introduces digital forms to replace or supplement those manual steps.

Existing workflow:
- users browse rooms and services through website pages
- customers request room info or place orders through forms
- authentication is required before login completes
- order and payment data are collected via forms
- reviews are stored centrally in a database

Manual processes:
- phone-based orders
- handwritten customer records
- manual payment notes
- guest feedback collected without centralized storage

Data handling:
- user registration stores name, email, phone, password
- orders store name, phone, address, food item, quantity, total price
- payments store personal billing data and last 4 digits only
- reviews store guest name, email, rating, and review text

Problems addressed:
- fragmented customer data
- slow order processing
- inconsistent customer record storage
- lack of digital review capture
- poor presentation of hotel services

Inefficiencies:
- manual management of rooms and orders
- delayed customer response
- absence of structured records

Security issues:
- manual data handling can lead to loss or misuse
- this project addresses some vulnerabilities through password hashing and card masking

Accessibility issues:
- no explicit accessibility framework is implemented; accessible design is limited to general semantic HTML and CSS.

Reporting problems:
- no formal report/dashboard module exists.

2.2 Limitations of Existing System

Limitation 1: No admin panel
Problem: There is no central place to manage records.
Cause: Project uses static frontend with basic PHP scripts, not a full management stack.
Impact: Business owners cannot easily manage orders, payments, and reviews.

Limitation 2: Booking workflow incomplete
Problem: A bookings table exists, but no frontend form is actively used to create room bookings.
Cause: Schema was created, but UI logic is not implemented.
Impact: Room booking capability is partially planned but not operational.

Limitation 3: Payment is simulated
Problem: Payment is not connected to real payment gateway integration.
Cause: No external payment library or provider integration is present.
Impact: It is not a live financial transaction system.

Limitation 4: No role-based authorization
Problem: There is no distinction between admin and regular user.
Cause: Session logic stores only basic user data.
Impact: User permissions and access control are not enforceable.

Limitation 5: Search bars are non-functional
Problem: Search inputs exist visually but do not trigger a real search backend.
Cause: Forms have no backend handler.
Impact: Search is cosmetic only.

Limitation 6: No route protection
Problem: Pages do not check whether a user is logged in before access.
Cause: No protected-route logic is implemented.
Impact: User authentication cannot be enforced across the site.

Limitation 7: Local-only deployment
Problem: No production deployment or environment configuration exists.
Cause: The system expects a local XAMPP setup.
Impact: It is not production-ready for live deployment.

2.3 Feasibility Study

Technical Feasibility:
This project is technically feasible because it uses common web stack components: HTML, CSS, JavaScript, PHP, and MySQL. XAMPP provides the local execution environment, and MySQLi in PHP supports database connectivity.

Economic Feasibility:
The project is cost-efficient because it uses free/open-source tools and no paid framework libraries. The main costs would be local hosting and maintenance if extended.

Operational Feasibility:
The website is easy to navigate and understand. Users can register, log in, and fill out forms without extensive training. However, no admin training module exists.

Schedule Feasibility:
This project fits a typical academic timeline because it uses a simple architecture with manageable modules and a limited number of forms and database tables.

Security and Legal Feasibility:
The application includes basic input validation, password hashing, and card-number masking. However, it lacks enterprise-level security mechanisms such as JWT, CSRF protection, route authorization, and live payment compliance.

2.4 Need of New System

The project is needed because manual handling of hotel and food service interactions is inefficient. The new system introduces digital convenience to:
- automate registration
- centralize data in a MySQL database
- process orders more quickly
- improve form validation and accuracy
- improve site presentation and user experience
- maintain user feedback records
- reduce paper-based and manual processing
- organize payment and order records centrally

4.7 Data Dictionary

Table: users
Purpose: store sign-up/login data
Relationships: none enforced; conceptual relation to orders/payments/reviews

Field details:
- id: INT, required, auto-increment, primary key
- full_name: VARCHAR(100), required, min validation in forms and server
- email: VARCHAR(150), required, unique, valid email check
- phone: VARCHAR(20), required, min 10 digits
- password: VARCHAR(255), required, password hashed
- created_at: TIMESTAMP, required, default CURRENT_TIMESTAMP

Table: orders
Purpose: store food orders

Field details:
- id: INT, required, auto-increment, primary key
- user_name: VARCHAR(100), required, min 2 chars
- phone: VARCHAR(20), required, min 10 digits
- address: VARCHAR(255), required
- food_item: VARCHAR(100), required
- quantity: INT, required, default 1, min 1
- total_price: DECIMAL(10,2), required, default 0.00
- status: ENUM('pending','confirmed','delivered','cancelled'), required, default pending
- ordered_at: TIMESTAMP, required, default CURRENT_TIMESTAMP

Table: payments
Purpose: store payment records

Field details:
- id: INT, required, auto-increment, primary key
- full_name: VARCHAR(100), required
- email: VARCHAR(150), required, valid email
- address: VARCHAR(255), required
- city: VARCHAR(100), required
- zip_code: VARCHAR(20), required
- card_name: VARCHAR(100), required
